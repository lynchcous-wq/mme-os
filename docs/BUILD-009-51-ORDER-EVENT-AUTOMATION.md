# Build 009.51 — Enterprise Customer Notification & Order Event Automation

## Scope
Provider-neutral event ingestion and dispatch orchestration for order, payment, fulfillment, pickup, return, refund, warranty and subscription lifecycle notifications. Delivery is delegated to Build 009.49; campaign and consent records remain in Build 009.50.

## Supported event types
`order_placed`, `payment_succeeded`, `payment_failed`, `shipment_label_created`, `shipment_in_transit`, `shipment_delivered`, `pickup_ready`, `pickup_reminder_due`, `return_authorized`, `refund_initiated`, `refund_completed`, `refund_failed`, `warranty_expiry_reminder_due`, `subscription_renewal_reminder_due`.

## Architecture
Authoritative commerce services publish a stable source event identifier to `mme_customer_order_notification_ingest_event`. A trusted worker claims/dispatches received events using configured channel rules and localized template keys. Dispatch jobs enter the Build 009.49 delivery outbox. Provider credentials and contact resolution remain in the trusted delivery worker, never in event payloads.

## Safety and correctness
- Unique source-system/event-id makes event ingestion idempotent.
- Stable event/person/channel keys prevent duplicate delivery jobs.
- Inactive identities and disabled channel preferences are suppressed and recorded.
- No marketing campaigns are generated by this transactional event pipeline.
- Event payloads should contain only approved, minimal, non-sensitive template variables; never payment-card data, credentials, full addresses or raw contact details.
- Delivery provider outcomes are recorded by Build 009.49; event dispatch means queued, not delivered.
- Event source authentication and signature verification must happen at the commerce API boundary before the service-role ingestion RPC is called.

## Operational integration required
Connect authoritative order, payment, shipping, pickup, returns, refunds, warranty and subscription domain events. Configure rules and localized templates for each desired event/channel. Deploy a scheduled worker with bounded retries, stale-processing recovery, alerting and dead-letter review. Do not infer shipment, refund or payment state from client-side callbacks.

## RPCs
- `mme_customer_order_notification_ingest_event(...)`
- `mme_customer_order_notification_dispatch_event(event_id, batch_size)`

## Observability
`mme_customer_order_notification_health` summarizes event state, queue counts and suppressions without exposing customer contact information.

## Validation
Run `npm run lint`, `npm run test:build009:order-event-automation`, `npm run test:build009:communications-hub`, and `npm run test:build009:notification-delivery`. PostgreSQL integration tests must verify duplicate source events, invalid identities, unknown rules, template absence, concurrent dispatch, preference suppression, event retry, partial completion, payload redaction and end-to-end outbox idempotency.

## Rollout boundary
Implementation branch only. No live order/payment/shipping/refund event producer, worker schedule, provider adapter, customer UI, push registration or production delivery is deployed by this migration.
